# ADR 0002：本地 SQLite 与追加式时间账本

- 状态：已接受
- 日期：2026-08-12

## 背景

TimeBet 不要求账号和服务器，但仍然需要在应用崩溃、重复点击和余额消费后保持学习记录可靠。学习历史不能因为兑换奖励或时间挑战而减少，因此历史学习数据和可用余额必须分离。

## 决策

1. 使用 SQLite 作为首版唯一持久化数据库。
2. 数据库文件和截图文件保存在用户本地应用数据目录。
3. 所有时间戳以 UTC Unix 毫秒保存，所有时长以整数秒保存。
4. `study_sessions` 保存学习时间块，`session_events` 保存状态转换，`session_tasks` 保存结束时的任务记录。
5. `ledger_entries` 使用追加式记录，余额由 `SUM(amount_seconds)` 计算。
6. 账本条目使用 SQLite 触发器禁止 UPDATE 和 DELETE。
7. 学习时间块完成、任务写入和 `Earn` 账本入账使用同一个事务。
8. 使用 SQLite WAL、外键、忙等待和迁移历史表。
9. 迁移文件以三位数字前缀排序，并且重复初始化必须幂等。

## 关键不变量

```text
累计学习时长 = 已完成学习时间块的有效时长之和
可用余额 = 所有账本条目的 amount_seconds 之和
一次最多存在一个 running 或 paused 时间块
已完成时间块必须有结束时间、有效时长和完成说明
账本条目只能追加，不能覆盖历史
```

## 理由

- 本地 SQLite 不需要部署服务，符合开源项目和学生用户的使用门槛。
- UTC 毫秒可以避免时区和夏令时影响时间排序。
- 整数秒避免浮点余额误差。
- 事务保证“完成学习但没有入账”或“入账但学习仍未完成”不会出现。
- 数据库约束和触发器为手工修正、崩溃恢复和未来同步提供稳定基础。

## 影响

- 阶段 2 的仓储仍然只覆盖学习会话和账本；奖励、截图和挑战表已建表，业务用例在后续阶段接入。
- 数据库迁移必须向后兼容，不能直接修改已经发布的迁移文件。
- 未来云同步需要同步账本事件，而不是同步一个可变余额字段。
- SQLite 文件和截图仍然是敏感本地数据，后续需要补充备份、加密和数据清理策略。
